\section{Data Sources}
\label{sec:data_sources}
In this work, we used publicly available \ac{AIS} data from three different environments to ensure diversity in traffic patterns, waterway types, and vessel behaviours.
The datasets cover measurement stations in three German cities, % Kiel,  Bremerhaven and Wedel, 
recorded by \ac{AIS} receivers operated by the Federal Maritime and Hydrographic Agency (Bundesamt für Seeschifffahrt und Hydrographie (BSH)) as part of their ship emissions monitoring programme. 
These data are organised by measurement station and month, downloadable per day, and publicly accessible via GovData. They are provided under the \emph{Data licence Germany – attribution – Version 2.0\footnote{\url{https://www.govdata.de/dl-de/by-2-0)}}}.
 %Datenlizenz Deutschland – Namensnennung – Version 2.0 sorry i was very careful not to translate it since the name was very explicit, but i found the official english version now
 For each measurement station, we used all data available for the year 2025 to cover a complete annual cycle and avoid bias to seasonal characteristics \parencite{bsh_ais_kiel_2025, bsh_ais_bremerhaven_2025, bsh_ais_wedel_2025}.

\paragraph{Raw Data Format.}

The \ac{AIS} data are stored as semicolon-delimited log files with fields including navigation status, heading, \ac{SOG}, latitude/longitude, \ac{COG}, true heading, and a UTC timestamp. % (YYMMDD HHMMSS)
The dataset assigns a unique identifier, the \ac{MMSI} to each vessel, allowing individual tracking.

\subsection{Data Extraction and Cleaning}
% more advanced filtering:https://arxiv.org/pdf/2001.01592
%\paragraph{Cleaning and Filtering.}

The first stage of the pipeline focuses on extracting dynamic position information and removing erroneous records.
Raw \ac{AIS} log files contain multiple message types beyond vessel position reports, including voyage-related data% (Type 5)
, static data reports%(Type 24)
, base station reports%(Type 4)
, and aids-to-navigation reports% (Type 21)
~\parencite{itu-r-m1371-1-2001}. 
To isolate relevant vessel movements, navigation aids (buoys etc.%, \ac{MMSI} starting with 99
) and aircraft were filtered out, and only message types carrying dynamic position information were retained%: Type 1 (Class A, scheduled), Type 2 (Class A, assigned), Type 3 (Class A, response), Type 18 (Class B), and Type 27 (long-range)
. These provide \ac{SOG}, \ac{COG}, heading, and coordinates. All other messages were discarded prior to parsing. This initial parsing reduced the raw dataset by approximately 15\%. 
During this extraction, known encoding errors were also corrected; %, by means such as adding constant value of 102.4 to all negative SOGs and converting a heading of 511 to NaN.
specifically, we added a constant offset of 102.4 to correct \ac{SOG} readings that were negative due to parsing errors, and converted the default heading values of 511 to missing data (NaN), as specified in \textcite{itu-r-m1371-1-2001}. % % If a parser uses signed instead of unsigned integers, in a 10-bit field this causes values above 511 to overflow into negative numbers. Adding 1024 steps (102.4 knots) corrects this binary two's complement error.
Additionally, duplicate records, which we define as two data points with the same timestamp and \ac{MMSI}, were resolved. 
Duplicates can occur when multiple stations receive the same signals. Approximately two-thirds of the duplicates were exact matches and were directly discarded in the cleaning process; 
the one-third that were not exact matches were handled by retaining the row with the fewest zero entries as the first criterion and the oldest row as the second criterion, respectively.

Following the initial extraction, the dataset was filtered for spatial and kinematic outliers. 
First, the data were restricted to specific geographic bounding boxes for each target region, as detailed in Table \ref{tab:geo-bounds}, which functioned as a primary filter for large coordinate errors. 
Following the approach by \textcite{articlebilstmsus}, within these boundaries, the dataset was further filtered by excluding any records with a reported \ac{SOG} exceeding 30 knots as implausible sensor or transmission errors.
In order to identify faulty \ac{GNSS} coordinates, we utilised the distance between consecutive points as follows: 
If the distance exceeded what is physically achievable based on the reported \ac{SOG} of the vessel and the time that elapsed since the previous timestamp, the point was discarded.
During this cleaning phase, no interpolation was performed to fill the resulting gaps.
This prevented the introduction of synthetic data before the formal resampling stage, which was not necessary because of the large number 
of available data points.
Our kinematic approach to filtering out implausible \ac{GNSS} positions %shows similarity to the more advanced positional preprocessing introduced by
aligns with the methods proposed by \textcite{Zhao_Shi_Yang_2018}, who filtered trajectories based on time gaps and physically implausible speed transitions.

Finally, because the \ac{ROT} is rarely transmitted by standard \ac{AIS} transponders, it was analytically derived as the time derivative of the \ac{COG}. To account for the circular nature of the \ac{COG} feature, we calculated $
\text{ROT} = \frac{((\Delta\text{COG} + 180) \bmod 360) - 180}{\text{freq\_s} / 60}
$ in degrees per minute. 
Positive values indicate a starboard turn and negative values a port turn.  %\\
To minimise the impact of \ac{GNSS} localisation noise, which causes fluctuations in \ac{COG} and thus artificial spikes in \ac{ROT} at low speeds, we applied two filters.
The first filter excluded segments with an \ac{SOG} below 0.5 knots. 
The second filter removed any remaining data points with a calculated absolute \ac{ROT} exceeding $90^\circ/\text{min}$.% A short discussion on the physical causes of these artifacts and the reasons for utilizing \ac{COG} despite these limitations is provided in Section \ref{subsubsec:kinematiclowvel}.
    





\subsection{Geographic Domain Assignment}


    
%\paragraph{Geographic Context Assignment.}
To enable the training of domain-aware models, each \ac{AIS} message was assigned a waterway type, based on its coordinates, hereafter referred to as the geographic \emph{domain}. We distinguish between \texttt{harbour}, \texttt{river}, \texttt{channel} and \texttt{lock} domain.
To assign those labels, we extracted water bodies and maritime infrastructure from \ac{OSM} via the OSMnx library \parencite{OpenStreetMap}, and matched vessel coordinates to these \ac{OSM} polygons using a spatial join following geometric buffering. %\\ %vlt das zitat hier raus, kommt ja noch in acknowledgements rein sowieso
Because explicit harbour tags in \ac{OSM} are often incomplete or unreliable, we employed a heuristic approach to classify waterway domains. 
First, we identified polygons tagged as locks, channels, and rivers (see Figure~\ref{fig:OSM_overview_Kiel} for the full taxonomy of domain types).
Any remaining valid water bodies within our bounding boxes that are not 
assigned to any of these types were defaulted to the \texttt{harbour} domain.

Furthermore, to account for \ac{GNSS} inaccuracies and completely unmapped open port basins, we expanded each \ac{OSM} polygon by a class- and dataset-specific radius before joining.
For instance, we used a large buffer for harbours to capture vessels in unmapped bays and applied smaller buffers for channels and locks.
In cases where these expanded polygons overlap, a priority mapping of \texttt{lock} > \texttt{river} > \texttt{channel} > \texttt{harbour} was applied to resolve conflicts (e.g., a lock is prioritised over a river). %\\    
Points that fell outside the buffered water polygons are labelled as \texttt{unknown} and excluded from the training data. Given the % heuristic 
 nature of this assignment, the resulting assignments were verified through manual visual inspection and the buffers tuned accordingly to ensure geographic validity. A visualisation of the label definitions in Kiel can be seen in Figure \ref{fig:OSM_overview_Kiel}, and the spatially assigned data applied to the Kiel and Bremerhaven datasets is illustrated in Figure \ref{fig:OSM_assigned}. The buffers are available in Table \ref{tab:buffer_radii}.

\subsection{Resampling} 

Accurate and consistent geometric distances are required for linear interpolation, for several motion models, and for our evaluation metrics.
Therefore, geographic coordinates were projected to the \ac{UTM}, for which the zone was determined automatically from the median longitude of each dataset.
The Cartesian representation ensures that linear interpolation produces geometrically correct intermediate positions, that normalisation operates on a uniform scale, and that Euclidean distance computations in loss functions are physically meaningful regardless of latitude.
Further details regarding the coordinate projection can be found in Figure \ref{fig:utm_overview} in Appendix~\ref{chap:appendixdataplots}.

To address temporal characteristics, the pipeline must account for non-uniform \ac{AIS} reporting frequencies%
%Having established a consistent spatial framework, the pipeline must also address temporal characteristics.
%The reporting frequency of \ac{AIS} transponders is not uniform
, because transmission intervals are dynamically adjusted based on vessel class, speed, and manoeuvring status %according to the messaging protocol  
\parencite{itu-r-m1371-1-2001}.
Class A transponders are mandatory for large commercial vessels (typically $>300$GT international or $>500$GT domestic) and transmit significantly more often than the Class B transponders used by smaller or recreational vessels. 
The resulting variable intervals (summarised in Table \ref{tab:ais-frequencies}) necessitate a standardised resampling approach. 
Therefore, the raw \ac{AIS} data were resampled to a uniform 30s grid, which captures our target speed range of 2 to 14 knots and ensures that both Class A and Class B transponders remain viable for model training. %\\
The interpolation method varied according to the feature type.
For most telemetry features, time linear interpolation was applied.
Geographic coordinates were interpolated using \ac{PCHIP}, which was preferred over natural cubic splines as the latter can produce oscillations near trajectory endpoints.
\ac{PCHIP} preserves monotonicity locally and yields smoother and more realistic trajectories than piecewise linear interpolation.
Categorical attributes, such as the domain, cannot be interpolated mathematically and are instead inherited from the last valid \ac{AIS} observation.%\\

We acknowledge that interpolating data adds patterns to our dataset that may also be learned by the motion models. 
To quantify the reliability of interpolated values, we computed a temporal offset feature, denoted as $\Delta t$.
This feature represents the absolute time difference between each resampled point and its nearest original observation:
$\Delta t = |t_{resampled} - t_{original, nearest}|$.
%\begin{equation*}
%\Delta t = |t_{resampled} - t_{original, nearest}|
%\end{equation*}
By including $\Delta t$ as a feature in subsequent modelling steps, the system can account for interpolation uncertainty.
A higher $\Delta t$ indicates lower confidence in the precision of the interpolated state at a 
specific timestamp.

\subsection{Trajectory Segmentation}

In this stage of the pipeline, cleaned trajectories are transformed into samples suitable for training. 
It includes the following steps: (1) Stratified Train-Validation-Test Splitting, (2) Sliding Window Segmentation, (3) Kinematic Filtering and (4) Data Augmentation.
In the following, these steps are explained in detail. 


\paragraph{Stratified Train-Validation-Test Splitting.}
\label{subsubsec:stratifiedtvtsplit}
In order to prevent data leakage, the dataset was partitioned at the vessel level rather than the sample level into a 70:15:15 train-validation-test split.
 %If the data were split randomly by trajectory% ID
 %, the sliding window stride would cause the model to see overlapping temporal segments of the same %vessel across the training and test sets. %hier noch eindeutiger eklären waum es reicht
 %One trajectory is, by construction, always associated to the same vessel.
 %Thus, splitting the data on the vessel level, we can make sure that no overlapping segments exist %between data splits.
 Since every sliding-window segment %(see the following paragraph for details)
 generated from a given vessel is assigned entirely to the same split, no vessel-level information can leak between training and evaluation, regardless of how densely the sliding window is sampled within a split.
If the data were instead split randomly by sample, the sliding window stride would cause the model to be trained and evaluated on overlapping temporal segments of the same vessel, which would constitute data leakage.
However, a simple random split at the vessel level is also insufficient due to the high diversity in vessel behaviour and the resulting class imbalance.
To ensure that each data split contains a representative distribution of motion dynamics, we used a stratified split based on $k$-means clustering.
Prior to the split, a three-dimensional feature vector was generated for each unique vessel, made of its mean velocity, maximum absolute \ac{ROT}, and primary geographic context.
These features were standardised using Z-score normalisation and clustered into five groups. The optimal number of strata was estimated using the elbow method on a small subset of the dataset. Further details about this estimation can be found in Figure \ref{fig:elbow_strat} in Appendix~\ref{chap:appendixdataplots}.
Finally, the stratified trajectories were saved separated by evaluation split and geographic domain, to enable targeted training and evaluation of the models.

\paragraph{Sliding Window Segmentation.} 
\label{subsubsec:windowandstride}
Next, trajectories were partitioned using a sliding window approach with a 5-minute context window and a 5-minute prediction horizon. 
This specific window size sits at the lower end of context lengths typically used in related inland literature \parencite{donandt2022shortterm, you2020stseq2seq}, and aligns with the collision risk alerting window considered practically
relevant for inland navigation \parencite{donandt2022shortterm}. 
To increase data utility, a 1-minute stride was applied between consecutive samples.
A temporal guard was implemented to discard segments where the elapsed time exceeded the theoretical duration ($T_{ctx} + T_{pred}$), to ensure that the models only learn from continuous motion sequences without gaps.
The guard simultaneously handled any gaps in the original data and the gaps we introduced with filters in previous preprocessing steps.
During this windowing process, generating completely homogeneous domain samples can be challenging due to \ac{GNSS} noise causing rapid label alternations near polygon borders.
To resolve this, a rolling majority vote over a 3-minute window (six samples at 30s frequency) was applied to smooth out label jitter. The trajectory was then split into sub-tracks when a persistent transition into a new geographic context occurred. Consequently, every sample includes only one domain. Since the domain is known at inference time, domain prediction was not required for this work.


\paragraph{Kinematic Filtering.}
To focus the model on active vessel dynamics rather than stationary behaviour, a two-tier speed filter was applied to every generated track. A sample was excluded if % it meets either of the following criteria:
the maximum \ac{SOG} within the segment did not exceed 0.5 knots or if more than 50\% of the data points within the segment reported an \ac{SOG} below 1.0 knots.
While these filters removed a significant portion of the raw data, they were essential for isolating manoeuvring patterns and preventing bias towards stationary or moored vessels. %\\
Notably, more than 90\% of points marked \texttt{lock} were filtered out in this step, %das ist nicht die gleiche analyse mit den 89 prozent, sonder hatte das einmal beim laufen gezäehlt mit und ohne
resulting in a loss of more than 98\% of the possible lock samples after further preprocessing, almost double the loss of all other domains at 50 to 60\%. This aligned with our expectations, given that vessels spend a lot of time stationary in those locks. The dynamics we are interested in, entry and exit, were not filtered out.

%\paragraph{Feature Engineering and Normalisation.}
\label{subsec:featureengineering}

The final stage of the preprocessing pipeline generates the motion features used as model inputs and standardises them to ensure numerical stability during training.
To ensure the deep learning models learn generalised motion patterns rather than memorising specific geographic locations, absolute \ac{GNSS} positions and projected ($x, y$) coordinates were deliberately omitted from the feature set. %search space
This forces the networks to learn generalisable vessel dynamics rather than location-specific patterns. 
Instead, absolute \ac{UTM} coordinates were converted into step-wise displacements ($dx, dy$) by calculating the difference between successive timestamps. Furthermore, to handle the $0^{\circ}/360^{\circ}$ wrap-around of the \ac{COG}, the angle was represented using its sine and cosine components.

%\paragraph{Standardisation and Leakage Prevention.}
Following the feature transformation, Z-score normalisation was applied.
To prevent data leakage, the normalisation parameters (mean $\mu$ and standard deviation $\sigma$) were strictly calculated from the training set. % This global scaler was then saved and applied to the validation and test sets without further modification. %\\
A single, global scaler was fitted this way and applied uniformly across all models and data subsets, including validation and test sets, without further modification. %
Using one shared scaler instead of a separate scaler per domain avoids introducing an additional source of variation between domain-specific models, but it also means that systematic scale differences between domains are not explicitly separated out at this stage.

The complete set of available features for model training is detailed in Table \ref{tab:unified-format}. The selection of which specific features to include for each model was handled %dynamically
using \ac{AutoML}, as specified in section \ref{subsub:featureselection}.
After Normalisation, the data were parsed into Parquet files for faster loading times and more efficient memory usage.

%\paragraph{Anonymisation.}
Finally, to prepare the dataset for publication and ensure privacy, vessels were anonymised via SHA-256 hashing of the \ac{MMSI}. 
We preserved positional privacy by expressing \acs{UTM} coordinates relative to median position of the dataset. 
This removes any absolute geographic reference.
